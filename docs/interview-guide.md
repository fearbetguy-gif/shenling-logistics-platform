# 神领物流项目面试讲解稿

这份文档只记录当前代码已经实现的内容，不把规划功能说成已完成。

## 一句话介绍

这是一个基于 Spring Boot 3、Spring Cloud Gateway、Nacos、MySQL、Redis 和 RabbitMQ 的精简物流微服务平台。用户下单后，订单服务保存订单并发布事件，运输服务异步创建运输任务；查询订单时优先读取 Redis，配送异常助手会先由后端校验权限并整理订单事实，再交给 Dify/DeepSeek 生成解释和建议。

## 一次完整请求怎么走

1. 前端请求 `Gateway:8090`，Gateway 根据路径转发到具体服务。
2. Gateway 从 `Authorization: Bearer <token>` 解析 JWT；登录、注册和内部健康检查走白名单。
3. 用户服务完成登录并签发 JWT，订单服务从 JWT 中取得用户 ID，不信任前端传入的用户 ID。
4. 创建订单时，后端校验地址归属、订单参数和 `X-Request-Id`。
5. Redis Lua 脚本原子地判断请求是否重复；通过后写入订单表，并发布 `order.created` 消息。
6. 运输服务消费消息，先用 `mq_consume_record` 的唯一约束做幂等，再创建运输任务。
7. 运输状态变化通过 Feign 同步订单服务；失败会写入补偿记录，后台任务按次数重试。
8. 用户查询订单时，订单详情先查 Redis，未命中才查询 MySQL；状态变化和取消订单会删除对应缓存。

## 面试官常问的核心问题

### 为什么要拆成多个服务？

按业务边界拆分，而不是按表拆分。用户服务负责身份和地址，订单服务负责订单状态，运输服务负责任务和轨迹。这样订单发布消息后，运输服务可以独立消费，订单服务不需要同步等待运输任务创建完成。

### Redis 缓存和数据库不一致怎么办？

当前实现采用 Cache-Aside：查询先读缓存，未命中读库并回填；更新数据库成功后删除缓存。删除缓存不是绝对一致方案，所以面试时要说明它适合本项目的最终一致场景；生产环境还可以增加延迟双删、消息通知或 CDC。

### 为什么创建订单要用 Lua？

“判断请求是否存在”和“写入幂等标记”必须是一个原子操作。若先 GET 再 SET，两个并发请求可能同时判断为空；Lua 脚本在 Redis 内一次执行，避免这个竞态。数据库唯一索引仍是最后一道防线。

### RabbitMQ 重复消费怎么处理？

消息至少一次投递，消费者不能假设只执行一次。消费前以 `message_type + message_key` 插入消费记录，数据库唯一约束保证同一业务消息只成功处理一次；重复消息直接确认并忽略。处理异常时重试，超过次数进入死信队列。

### 为什么消息不能只靠 ACK 保证不重复？

ACK 只表示消息是否从队列确认，不等于业务数据库事务和 ACK 是同一个原子事务。消费者可能已经写库但还没 ACK 就宕机，RabbitMQ 会重新投递，所以业务幂等必须由消费记录或业务唯一键保证。

### Dify/DeepSeek 在项目里负责什么？

后端负责可信数据：登录用户是否拥有订单、订单当前状态、轨迹、异常规则和可执行动作。Dify/DeepSeek 负责自然语言理解和表达，不能直接修改订单或发起赔付。即使模型返回了建议，真正执行仍要回到后端接口做权限和状态校验。

### 路径预测算法是什么？

当前实现不是机器学习预测，而是基于数据库路网的 Dijkstra 最短路径算法。节点和边来自 `route_node`、`route_edge`，边权是公里数；算法用优先队列每次取当前距离最小的节点，并松弛相邻边。它适合当前演示版的静态路网；如果以后加入实时拥堵、天气和历史时长，可以把动态权重接入或再训练预测模型。

### 为什么状态不能直接改成任意字符串？

状态机把允许的业务迁移集中在枚举中，例如已签收和已取消不能继续流转。这样 Controller 只接收目标状态，Service 调用 `canTransitTo` 校验，避免把非法流程散落在多个接口里。

## 诚实的项目边界

- 当前路线算法是静态路网最短路径，不宣称已经实现实时导航或机器学习预测。
- 当前 AI 是 Dify/DeepSeek 辅助解释，不宣称实现了自动理赔、自动调度或自主修改订单。
- 当前测试是单元测试和接口验证，不宣称做过高并发压测。
- 当前缓存策略是删除缓存实现最终一致，面试时应主动说明更高一致性场景的升级方案。

## 推荐演示顺序

1. 登录拿 JWT。
2. 创建订单并携带相同 `X-Request-Id` 重复请求，展示幂等结果。
3. 查询订单两次，说明第一次查库回填、第二次命中 Redis。
4. 在 RabbitMQ 管理页面展示订单事件和运输任务创建结果。
5. 领取任务并按状态机更新运输状态，查询轨迹。
6. 调用最短路径接口展示 `WAREHOUSE -> ... -> CUSTOMER`。
7. 调用配送异常助手，说明后端事实、规则和 Dify 自然语言回答的边界。
